# سيناريوهات استخدام FixFlow

هذا المستند يشرح كيف تتحرك الأدوار الأساسية داخل FixFlow من لحظة فتح طلب الصيانة حتى إصدار التقرير والفاتورة.

## 1. سيناريو العميل يفتح طلب صيانة

المستخدم: `customer`

البداية:

يدخل العميل إلى بوابة العميل عبر `/customer/dashboard`، ويرى أجهزته وطلباته المفتوحة وآخر الحالات.

الخطوات:

1. يفتح العميل صفحة إنشاء طلب صيانة.
2. يختار الجهاز المرتبط بحسابه، مثل مكيف غرفة الاجتماعات.
3. يكتب عنوان المشكلة، مثل "المكيف لا يبرد".
4. يضيف وصفًا واضحًا للمشكلة.
5. يحدد التاريخ المفضل للزيارة.
6. يختار أولوية الطلب.
7. يرسل الطلب.

ما يحدث في النظام:

- يتم إنشاء `ServiceRequest` بحالة `new`.
- يتم ربط الطلب بـ `company_id`, `customer_id`, و`service_asset_id`.
- يتم تسجيل حدث في `audit_logs`.
- يتم إرسال notification إلى dispatchers النشطين داخل نفس الشركة.

قيد الحماية:

العميل لا يستطيع اختيار جهاز تابع لعميل آخر، لأن التحقق يتم داخل Form Request وليس في الواجهة فقط.

## 2. سيناريو dispatcher يراجع ويعين فني

المستخدم: `dispatcher`

البداية:

يدخل dispatcher إلى `/dispatch/dashboard` ليرى ضغط اليوم، الطلبات المفتوحة، الطلبات المتأخرة، وتوزيع الأولويات.

الخطوات:

1. يفتح قائمة طلبات الصيانة.
2. يراجع الطلبات الجديدة.
3. ينقل الطلب من `new` إلى `under_review`.
4. يحدد الفني المناسب.
5. يختار موعد الزيارة وموقعها.
6. يضغط تعيين الفني.

ما يحدث في النظام:

- إذا كان الطلب `under_review`، ينتقل تلقائيًا إلى `scheduled` عند تعيين الفني.
- يتم إنشاء `ServiceVisit` مرتبطة بالطلب.
- يتم إرسال notification للفني.
- يتم تسجيل عملية التعيين في `audit_logs`.

قيد الحماية:

لا يستطيع dispatcher تعيين فني من شركة أخرى، ولا يستطيع تعيين مستخدم لا يحمل دور `technician` أو حالته غير `active`.

## 3. سيناريو الفني ينفذ الزيارة

المستخدم: `technician`

البداية:

يدخل الفني إلى `/technician/dashboard` ويرى زيارات اليوم والزيارات القادمة والطلبات قيد التنفيذ.

الخطوات:

1. يفتح صفحة `My Visits`.
2. يفتح تفاصيل الزيارة المسندة له.
3. يراجع بيانات العميل والجهاز ووصف المشكلة.
4. يضغط بدء الزيارة.
5. يضيف ملاحظات فنية أثناء العمل.
6. يضيف التشخيص والحل وقطع الغيار المستخدمة.
7. يرفع صور قبل وبعد إن توفرت.
8. ينهي الزيارة ويغلق الطلب عند اكتمال الإصلاح.

ما يحدث في النظام:

- تنتقل الزيارة إلى `in_progress` عند البدء.
- يمكن نقل الطلب إلى `in_progress`, `waiting_parts`, أو `completed` حسب الحالة المسموحة.
- عند الإكمال يتم تحديث `completed_at`.
- يتم إنشاء أو تحديث `ServiceReport`.
- يتم تسجيل الإغلاق والتقرير في `audit_logs`.
- يتم إشعار العميل بتغير الحالة.

قيد الحماية:

الفني يرى فقط الزيارات التي تحمل `technician_id` الخاص به، ولا يستطيع فتح أو تعديل زيارة غير مسندة له.

## 4. سيناريو الشركة تصدر تقرير وفاتورة

المستخدم: `company_admin`

البداية:

بعد اكتمال الطلب ووجود تقرير صيانة، يدخل مدير الشركة إلى تفاصيل الطلب.

الخطوات:

1. يراجع بيانات الشركة والعميل والجهاز.
2. يراجع التشخيص والحل وقطع الغيار المستخدمة.
3. يضغط Generate PDF.
4. ينشئ فاتورة من الطلب.
5. يحدد تكلفة الخدمة ونسبة الضريبة.
6. يصدر الفاتورة أو يحفظها كمسودة.
7. عند الدفع يضغط Mark as Paid.

ما يحدث في النظام:

- يتم إنشاء PDF داخل storage وتحديث `service_reports.pdf_path`.
- يتم حساب:
  - تكلفة الخدمة.
  - تكلفة قطع الغيار.
  - subtotal.
  - tax.
  - total.
- يتم إنشاء `Invoice` مرتبطة بالطلب.
- يمكن تغيير حالة الفاتورة إلى `paid`.

قيد الحماية:

الفاتورة لا تنشأ إلا من طلب مكتمل، ولا يستطيع مستخدم من شركة أخرى رؤيتها أو تعديلها.

## 5. سيناريو super_admin يدير الشركات

المستخدم: `super_admin`

البداية:

يدخل super admin إلى `/platform/dashboard`.

الخطوات:

1. يراجع عدد الشركات الكلي.
2. يراجع عدد الشركات النشطة.
3. يراجع إجمالي المستخدمين.
4. يراجع عدد طلبات الصيانة في النظام كله.
5. يراقب توزيع الطلبات حسب الحالة.

ما يحدث في النظام:

- يتم حساب مؤشرات المنصة بدون تقييد `company_id`.
- الوصول لهذه اللوحة محمي بدور `super_admin` وصلاحية إدارة الشركات.

قيد الحماية:

مستخدمو الشركات لا يستطيعون الوصول إلى لوحة المنصة، حتى إذا أخفينا الرابط أو حاولوا فتح الرابط مباشرة.
