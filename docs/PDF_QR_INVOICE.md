# QR وPDF والفواتير في FixFlow

يوثق هذا الملف ثلاث ميزات احترافية تمت إضافتها إلى FixFlow:

- QR Code لكل جهاز.
- تقرير PDF لطلب الصيانة.
- فاتورة بسيطة مرتبطة بطلب الصيانة.

## QR Code للأجهزة

كل جهاز في جدول `service_assets` يحتوي على الحقل `qr_code`. عند إنشاء جهاز جديد بدون قيمة QR، يقوم Model `ServiceAsset` بتوليد token فريد تلقائيًا بصيغة مثل:

```text
asset_01k4...
```

تستخدم خدمة `ServiceAssetQrCodeService` حزمة `bacon/bacon-qr-code` لتوليد SVG يحتوي رابط صفحة الجهاز:

```text
/assets/qr/{qrCode}
```

### ماذا يرى من يمسح QR؟

الصفحة العامة تعرض معلومات محدودة فقط:

- اسم الجهاز.
- النوع.
- الماركة.
- الموديل.
- الرقم التسلسلي.
- حالة الضمان.

لا تظهر بيانات العميل أو سجل الصيانة للضيف. إذا كان المستخدم مسجل الدخول ومصرحًا له برؤية الجهاز، تظهر له آخر طلبات الصيانة.

### مثال

جهاز:

- الاسم: `Conference Room AC`
- النوع: `air_conditioner`
- الماركة: `CoolAir`
- الموديل: `CA-24000`
- الرقم التسلسلي: `FF-AC-0001`
- الضمان: ساري حتى تاريخ محدد

عند مسح QR من شخص غير مسجل، يرى فقط هذه البيانات العامة. عند المسح من مدير الشركة أو العميل صاحب الجهاز أو الفني المسند لطلبات هذا الجهاز، يمكن عرض سجل الصيانة المسموح به.

## PDF Service Report

يتم توليد تقرير PDF من طلب صيانة مكتمل يحتوي على تقرير نهائي. تستخدم الخدمة `ServiceReportPdfService` حزمة `barryvdh/laravel-dompdf`.

المسار:

```text
POST /service-requests/{serviceRequest}/report/pdf
```

الحماية تتم عبر Policy:

```php
generateReportPdf
```

ولا يسمح بالتوليد إلا إذا:

- المستخدم من نفس الشركة.
- الطلب مكتمل `completed`.
- يوجد تقرير صيانة مرتبط بالطلب.
- المستخدم لديه صلاحية `view reports` أو يملك حق رؤية الطلب حسب دوره.

### محتوى PDF

يحتوي التقرير على:

- رقم الطلب.
- بيانات الشركة.
- بيانات العميل.
- بيانات الجهاز.
- وصف المشكلة.
- التشخيص.
- الحل.
- قطع الغيار المستخدمة.
- اسم الفني.
- تاريخ الزيارة.
- توقيع العميل إن وجد.

### مثال بيانات

طلب صيانة:

- رقم الطلب: `#12`
- المشكلة: `المكيف لا يبرد`
- التشخيص: `ضعف في مكثف الضاغط`
- الحل: `تم استبدال المكثف واختبار دورة التبريد`
- الفني: `Field Technician`
- القطع: `AC Capacitor 45uF`

بعد الضغط على زر `Generate PDF` يتم حفظ الملف داخل:

```text
storage/app/public/reports/service-requests/
```

ويتم تخزين المسار في:

```text
service_reports.pdf_path
```

## Invoice

يمكن إنشاء فاتورة واحدة لكل طلب صيانة مكتمل فقط. جدول `invoices` يحتوي الآن على تفصيل الحساب:

- `service_cost`
- `parts_total`
- `tax_rate`
- `subtotal`
- `tax`
- `total`

المسار:

```text
POST /service-requests/{serviceRequest}/invoice
```

صفحة العرض:

```text
/invoices/{invoice}
```

تعليم الفاتورة كمدفوعة:

```text
POST /invoices/{invoice}/mark-paid
```

## حالات الفاتورة

| الحالة | المعنى |
| --- | --- |
| `draft` | مسودة غير مصدرة. |
| `issued` | فاتورة مصدرة للعميل. |
| `paid` | تم دفعها. |
| `cancelled` | ملغاة. |

## مثال حساب فاتورة

بيانات:

- تكلفة الخدمة: `100.00`
- قطع الغيار: قطعتان × `10.00` = `20.00`
- نسبة الضريبة: `15%`

الحساب:

```text
subtotal = 100.00 + 20.00 = 120.00
tax = 120.00 × 0.15 = 18.00
total = 120.00 + 18.00 = 138.00
```

تسجل عملية إنشاء الفاتورة في `audit_logs` كحدث:

```text
invoice_created
```

وعند تعليمها كمدفوعة يسجل الحدث:

```text
invoice_paid
```
